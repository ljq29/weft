# Weft 设计

好问题。给 agent 做软件，文档的核心作用是**把你脑子里的隐性知识变成显性约束**，减少 agent 猜测和跑偏。通常一套够用的文档如下：

## 建议的文档集

|文档|回答什么问题|达成的效果|
| ------| ----------------------------------------------------| ---------------------------------------------------------------------------------------------------------------|
|**1. 产品需求文档（PRD）**|做什么、为谁做、为什么做、不做什么|定边界。agent 最容易犯的错是"过度设计"或"理解偏差"，PRD 里的目标用户、核心场景、明确的 Non-goals 能压住这两点|
|**2. 用户故事 / 验收标准**|每个功能"完成"的定义是什么|可验证。用 Given/When/Then 写，agent 能直接转成测试用例，你也能据此验收|
|**3. 架构设计文档（ADR / Design Doc）**|系统怎么拆、模块怎么交互、技术选型及理由|防止 agent 每次会话重新发明结构。记录"为什么不选 X"尤其重要，否则 agent 会反复提议改回去|
|**4. 数据模型 / 接口契约**|实体、字段、关系；API 的输入输出|这是最值得写细的部分。模块间的契约定死后，agent 可以并行、独立地实现各模块而不互相破坏|
|**5. 工程规范（CLAUDE.md / CONTRIBUTING）**|语言版本、目录结构、命名、lint、测试命令、提交规范|让 agent 的产出风格一致，且知道如何自检（跑哪条命令验证）|
|**6. 任务拆解 / 里程碑（Roadmap / Tasks）**|按什么顺序做、每步交付什么|控制单次任务粒度。agent 一次做太多容易失控，拆成可独立验证的小步最稳|
|**7. 测试策略**|哪些层要测、覆盖到什么程度、怎么跑|给 agent 一个"我做完了"的客观判定标准|

对于中小型项目，1、3、4、5、6 是必需的，2 和 7 可以合并进其他文档。

## 几个经验

-  **"不做什么"比"做什么"更有价值**，agent 很擅长扩展，不擅长克制。
- **决策要带理由**，否则 agent 会在后续会话中"好心地"推翻它。
- **接口和数据模型要具体到字段级别**，这是歧义最大的地方。
- 文档之间要**互相引用而非重复**，否则改一处漏一处，agent 会读到矛盾信息。

## 建议的对话流程

1. 你先用几句话描述软件的构思：解决什么问题、给谁用、你设想的核心体验
2. 我追问澄清，一起敲定 PRD（目标、场景、范围、Non-goals）
3. 基于 PRD 讨论架构和技术选型，产出设计文档
4. 细化数据模型和接口契约
5. 定工程规范和任务拆解
6. 最后我把所有内容整理成一组可直接放进仓库的 Markdown 文件

那就从第一步开始吧：**你想做的是什么软件？解决什么问题、给谁用？**
